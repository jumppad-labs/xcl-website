Plenty of configuration only needs to be read. Nothing is created in the
outside world, you just want the values, with references, variables and
modules resolved, as ordinary Go structs.

That is what this example shows. The block types are plain Go types
registered on the plugin registry with `RegisterType`. xcl decodes each block
into your type, resolves every reference in dependency order, and never calls
a provider. A registered type needs nothing else: no plugin, no provider, no
schema to write by hand.

The configuration is a small Kubernetes-like deployment, with the names a
Kubernetes user would recognise rather than a literal translation of a
manifest. The source is in
[`example/configonly`](https://github.com/jumppad-labs/xcl/tree/main/example/configonly).

## The Go types

A block type is a struct embedding `types.ResourceBase`, which carries the
common block metadata and the `depends_on` and `disabled` attributes.
Anything nested inside a block is a plain struct: a block that appears once
is a pointer, a block that repeats is a slice.

```go title="example/configonly/resources/resources.go"
// ConfigMap defines the block type `config_map`, a bag of values the
// deployment reads. A map attribute holds values whose names are not known
// ahead of time, and a single value can be read from it with
// `resource.config_map.api.data.db_host`.
type ConfigMap struct {
	types.ResourceBase `xcl:",remain"`

	Data map[string]string `xcl:"data" json:"data"`
}

// Deployment defines the block type `deployment`. It holds repeated container
// blocks, each of which nests further blocks of its own.
type Deployment struct {
	types.ResourceBase `xcl:",remain"`

	Replicas int `xcl:"replicas,optional" json:"replicas,omitempty"`

	// Containers is a repeated block, one entry per container block in the
	// configuration. A repeated block is a slice, a block that appears once is
	// a pointer.
	Containers []Container `xcl:"container,block" json:"container"`

	// Volumes are mounted by the containers above through their name
	Volumes []Volume `xcl:"volume,block" json:"volume,omitempty"`
}

// Container is the nested `container` block of a deployment. It is not a
// resource of its own, so it does not embed types.ResourceBase and can not be
// referenced by its own id, its fields are reached through the deployment
// that holds it, i.e.
// `resource.deployment.api.container[0].port[0].container_port`.
type Container struct {
	Name  string `xcl:"name" json:"name"`
	Image string `xcl:"image" json:"image"`

	Ports []Port   `xcl:"port,block" json:"port,omitempty"`
	Env   []EnvVar `xcl:"env,block" json:"env,omitempty"`

	// Resources appears at most once, so it is a pointer and is nil when the
	// container does not set it
	Resources *ResourceRequirements `xcl:"resources,block" json:"resources,omitempty"`

	VolumeMounts []VolumeMount `xcl:"volume_mount,block" json:"volume_mount,omitempty"`
}
```

The `service` type shows why this is more than a manifest. Kubernetes matches
a service to its pods with a label selector, because a manifest has no way to
point at another object. Configuration parsed by xcl does, so the service
names the deployment by its id and reads the port out of it, and the two can
not drift apart.

```go title="example/configonly/resources/resources.go"
type Service struct {
	types.ResourceBase `xcl:",remain"`

	Deployment string `xcl:"deployment" json:"deployment"`
	Port       int    `xcl:"port" json:"port"`
	TargetPort int    `xcl:"target_port" json:"target_port"`
}
```

## The configuration

Variables, a map attribute, blocks nested inside blocks, blocks that repeat,
and references between resources, including a reference into a repeated block
by position.

```hcl title="example/configonly/config/main.xcl"
variable "image_tag" {
  default = "1.2.0"
}

variable "replicas" {
  default = 3
}

# config_map holds values whose names are not known to the Go type, its data
# is a map. The deployment reads single values out of it below.
resource "config_map" "api" {
  data = {
    db_host   = "postgres.default.svc"
    log_level = "info"
  }
}

resource "deployment" "api" {
  replicas = variable.replicas

  # container is a repeated block, this deployment has two of them
  container {
    name  = "api"
    image = "ghcr.io/example/api:${variable.image_tag}"

    # port is repeated in turn, a block nested inside a block
    port {
      name           = "http"
      container_port = 8080
    }

    port {
      name           = "metrics"
      container_port = 9090
    }

    # env values are read from the config map, so they are declared once
    env {
      name  = "DB_HOST"
      value = resource.config_map.api.data.db_host
    }

    env {
      name  = "LOG_LEVEL"
      value = resource.config_map.api.data.log_level
    }

    # resources nests two more blocks of its own
    resources {
      limits {
        cpu    = "500m"
        memory = "512Mi"
      }

      requests {
        cpu    = "100m"
        memory = "128Mi"
      }
    }

    volume_mount {
      name = "config"
      path = "/etc/api"
    }
  }

  container {
    name  = "proxy"
    image = "ghcr.io/example/proxy:0.4.1"

    port {
      name           = "proxy"
      container_port = 8081
    }
  }

  volume {
    name       = "config"
    config_map = resource.config_map.api.meta.id
  }
}

# The service is linked to the deployment by its id. The port it sends traffic
# to is read out of the deployment as well. A repeated block is referenced by
# position, container[0] is the first container block.
resource "service" "api" {
  deployment  = resource.deployment.api.meta.id
  port        = 80
  target_port = resource.deployment.api.container[0].port[0].container_port
}

resource "ingress" "api" {
  host = "api.example.com"

  rule {
    path    = "/"
    service = resource.service.api.meta.id
    port    = resource.service.api.port
  }
}

output "api_url" {
  value = "https://${resource.ingress.api.host}"
}
```

## The program

Register each Go type under the block type name used in configuration, give
the config a state store, and apply. `run` takes the receiver for xcl's
[events](/events/) as `handler`, and `main` passes it the example's pretty
terminal receiver in one line:

```go title="example/configonly/main.go"
_, err = run(os.Stdout, prettylog.Handler(os.Stderr, prettylog.LevelFromEnv()), dir, filepath.Join(stateDir, "state.json"))
```

The registry takes no logger, and xcl writes nothing unless a receiver is set.

```go title="example/configonly/main.go"
r := registry.NewPluginRegistry()

// Register each Go type under the block type name used in configuration.
// A registered type needs nothing else: no plugin, no provider, no schema
// to write by hand.
if err := r.RegisterType("config_map", &resources.ConfigMap{}); err != nil {
	return nil, err
}

if err := r.RegisterType("deployment", &resources.Deployment{}); err != nil {
	return nil, err
}

if err := r.RegisterType("service", &resources.Service{}); err != nil {
	return nil, err
}

if err := r.RegisterType("ingress", &resources.Ingress{}); err != nil {
	return nil, err
}

// Keep the state in a file, Destroy works from it alone
store, err := state.NewFileStateStore(statePath, r)
if err != nil {
	return nil, err
}

c := xcl.NewConfig(
	xcl.WithPluginRegistry(r),
	xcl.WithStateStore(store),
	xcl.WithEventHandler(handler),
)

if err := c.Apply(dir); err != nil {
	return nil, err
}
```

`FindByType` and `Find` hand the entities back as your own Go types, by kind or
by path, and everything nested inside them is an ordinary Go struct or slice.

```go title="example/configonly/main.go"
deployments, err := xcl.FindByType[resources.Deployment](c, "resource", "deployment")
if err != nil {
	return err
}

for _, d := range deployments {
	for _, container := range d.Containers {
		for _, port := range container.Ports {
			fmt.Fprintf(out, "      port %s container_port=%d\n", port.Name, port.ContainerPort)
		}

		// A block that appears once is a pointer, nil when the
		// configuration leaves it out
		if container.Resources != nil {
			fmt.Fprintf(out, "      limits cpu=%s memory=%s\n", container.Resources.Limits.CPU, container.Resources.Limits.Memory)
		}
	}
}
```

## Run it

From the `example/configonly` directory:

```bash
make run
```

The events go to standard error, trimmed here to a few of each. Every step is logged at info, `core` is xcl
itself, and each line names the resource and the file it came from. The
level is read from `XCL_LOG_LEVEL` and defaults to info:

```text
1:01PM INFO apply start source=core operation=apply phase=start
1:01PM INFO parse success source=core operation=parse phase=success resource=resource.config_map.api type=config_map.api file=config/main.xcl
1:01PM INFO parse success source=core operation=parse phase=success resource=resource.deployment.api type=deployment.api file=config/main.xcl
1:01PM INFO create success source=core operation=create phase=success resource=resource.config_map.api type=config_map.api file=config/main.xcl
1:01PM INFO create success source=core operation=create phase=success resource=resource.deployment.api type=deployment.api file=config/main.xcl
1:01PM INFO create success source=core operation=create phase=success resource=resource.service.api type=service.api file=config/main.xcl
1:01PM INFO create success source=core operation=create phase=success resource=resource.ingress.api type=ingress.api file=config/main.xcl
1:01PM INFO apply success source=core operation=apply phase=success duration=11.970556ms
```

No registered type has a provider, so each block goes straight to `create
success` with no `start` in between. The program's own output, on standard
output, is the parsed configuration:

```text
## Resources
  resource.config_map.api
  resource.deployment.api
  resource.service.api
  resource.ingress.api
  output.api_url
  variable.image_tag
  variable.replicas
## Deployments
  resource.deployment.api replicas=3
    container api image=ghcr.io/example/api:1.2.0
      port http container_port=8080
      port metrics container_port=9090
      env DB_HOST=postgres.default.svc
      env LOG_LEVEL=info
      limits cpu=500m memory=512Mi
      requests cpu=100m memory=128Mi

      port proxy container_port=8081

  resource.service.api deployment=resource.deployment.api port=80 target_port=8080

  resource.ingress.api host=api.example.com
    rule path=/ service=resource.service.api port=80

  0 resources remaining
```

## What to notice

- **Values are declared once.** The service's `target_port` is read out of
  the deployment's first container port, so changing the container port
  changes the service too. The environment variables come from the config
  map the same way.
- **Resources are linked, not matched.** The service names the deployment by
  id and the ingress names the service by id. There is no selector to keep in
  sync by hand.
- **References order the graph.** The ingress reads the service, which reads
  the deployment, which reads the config map, so they are always parsed in
  that order, and blocks that do not depend on each other are processed
  concurrently.
- **Nesting is just Go.** `container[0].port[0]` in configuration is
  `Containers[0].Ports[0]` in Go, and an omitted block is nil.
