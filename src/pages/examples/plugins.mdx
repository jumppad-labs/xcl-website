When a block stands for something real, a network, a container, a file on
disk, it needs a lifecycle. In xcl that lifecycle belongs to a **provider**:
a type with `Create`, `Read`, `Changed`, `Update` and `Destroy` methods that
xcl calls as a configuration is applied and destroyed. Providers are packaged
in **plugins**, and a plugin provides as many block types as it likes.

This example applies a configuration with three block types, provided by two
plugins that do real work:

- **The Docker plugin** is an external plugin, compiled to its own binary,
  `docker-plugin`. xcl starts it as a separate process and calls it over
  gRPC. It provides `docker "network"` and `docker "container"`, and creates
  real Docker networks and containers through the Docker Engine SDK.
- **The template plugin** is an in-process plugin, `TemplatePlugin`,
  compiled into the program. It provides `template`, a block type with no
  subtype, and renders a Handlebars template to a file.

Because the Docker plugin creates real containers, the example needs a Docker
engine, reached through `DOCKER_HOST` or the default socket. The source is in
[`example/plugin`](https://github.com/jumppad-labs/xcl/tree/main/example/plugin).

A computed value crosses from one plugin to the other. Docker only assigns a
container its address when the container is created, so `ip_address` is a
computed field: the Docker plugin's provider fills it in, in the plugin
process. The template reads that address in its variables, so xcl creates
the container first and hands the address, already resolved, to the
in-process template provider, which writes it into the rendered file.

## The configuration

The configuration is a network, a container on it, and a template that
describes where the container can be reached:

```hcl title="example/plugin/config/main.xcl"
# The configuration the plugin example applies. The docker blocks come from
# the external Docker plugin, the template block from the in-process template
# plugin.
#
# Variables can be overridden with environment variables prefixed HCL_VAR_,
# i.e. HCL_VAR_output_dir.

# output_dir is where the rendered template is written
variable "output_dir" {
  default = "./build/rendered"
}

# A Docker bridge network named app. The Docker plugin sets the computed
# docker_id when it creates it.
docker "network" "app" {
  subnet = "10.42.0.0/24"
}

# An nginx container named web on the app network. Referring to the network
# orders the blocks, web is always created after app and destroyed before it.
docker "container" "web" {
  image = "nginx:1.27-alpine"

  # a nested block, repeated once per network the container joins
  network {
    name    = docker.network.app.meta.name
    aliases = ["web"]
  }
}

# template has no subtype, so it takes just a name. Its variables read the
# container's ip_address, which the Docker plugin computes when it creates the
# container, so a value crosses from the external plugin to the in-process
# one.
template "welcome" {
  source = <<-EOF
  Welcome to the {{network}} network.
  The web container answers at http://{{address}}/
  EOF

  destination = "${variable.output_dir}/welcome.txt"

  variables = {
    network = docker.network.app.meta.name
    address = docker.container.web.ip_address
  }
}
```

## The types

Each block type is a Go struct embedding `types.ResourceBase`. The container
has two computed fields, `docker_id` and `ip_address`, marked `computed` in
their tags. They can not be set in configuration, only a provider can fill
them in. Its nested `network` block is a slice of `NetworkAttachment`, one
entry for each `network` block the container has:

```go title="example/plugin/plugins/docker/resources/container.go"
// Container defines the block type docker "container", a Docker container
// named after the block
type Container struct {
	types.ResourceBase `xcl:",remain"`

	// Image is the image the container runs, it is pulled when Docker does
	// not have it
	Image string `xcl:"image" json:"image"`

	// Command overrides the image's command
	Command []string `xcl:"command,optional" json:"command,omitempty"`

	// Environment holds the container's environment variables
	Environment map[string]string `xcl:"environment,optional" json:"environment,omitempty"`

	// Networks are the networks the container joins, one nested network block
	// each. The container is created on the first and connected to the rest.
	Networks []NetworkAttachment `xcl:"network,block" json:"network,omitempty"`

	// DockerID is computed, the ID Docker gives the container
	DockerID string `xcl:"docker_id,optional,computed" json:"docker_id,omitempty"`

	// IPAddress is computed, the container's address on its first network
	IPAddress string `xcl:"ip_address,optional,computed" json:"ip_address,omitempty"`
}

// NetworkAttachment is a nested network block of a docker "container" block
type NetworkAttachment struct {
	// Name is the Docker name of the network, i.e. docker.network.app.meta.name
	Name string `xcl:"name" json:"name"`

	// Aliases are extra names the container is known by on the network
	Aliases []string `xcl:"aliases,optional" json:"aliases,omitempty"`
}
```

`resources.Network` is built the same way, with a `subnet` and a computed
`docker_id`.

## The Docker plugin

A plugin embeds `plugins.PluginBase` and registers the block types it
provides in `Init`, calling `RegisterResourceProvider` once per type with
the type's Go struct and its provider. The Docker plugin builds one Docker
client first and gives it to both providers. The logger `Init` receives is
plugin scoped: it is for messages written outside a provider call, and xcl
names the plugin as the source of everything it logs.

```go title="example/plugin/plugins/docker/plugin.go"
// Init builds the Docker client from the environment and registers both block
// types, each with a provider holding that client. Building the client does
// not contact Docker, the providers do when they are called.
//
// logger is plugin scoped, for messages written outside a provider call like
// this one. xcl adds provider=<block subtype> to what each provider's Init
// logs. During a call the providers log through plugins.Logger(ctx) instead,
// which xcl binds to the resource and step being worked on.
func (p *Plugin) Init(logger logger.Logger, state plugins.State) error {
	dockerClient, err := client.New()
	if err != nil {
		return err
	}

	logger.Debug("registering block types", "block_types", "docker.network, docker.container")

	err = plugins.RegisterResourceProvider(
		&p.PluginBase,
		logger,
		state,
		"docker",
		"network",
		&resources.Network{},
		resources.NewNetworkProvider(dockerClient),
	)
	if err != nil {
		return err
	}

	return plugins.RegisterResourceProvider(
		&p.PluginBase,
		logger,
		state,
		"docker",
		"container",
		&resources.Container{},
		resources.NewContainerProvider(dockerClient),
	)
}
```

### The providers

The providers never use the Docker SDK client directly. They hold a
`client.Docker`, a narrow interface listing only the SDK methods they call,
each with the SDK's own signature. It lives in its own package,
`plugins/docker/client`, alongside `New`, which builds the real client from
the environment, and `Ping`, which checks an engine answers. The real SDK
`*client.Client` satisfies the interface with no adapter, and the unit tests
use a mock generated from it:

```go title="example/plugin/plugins/docker/client/client.go"
// Docker is the part of the Docker Engine SDK client the providers use. Each
// method has the same signature as the SDK's, so *client.Client satisfies it.
type Docker interface {
	Ping(ctx context.Context) (types.Ping, error)

	NetworkCreate(ctx context.Context, name string, options network.CreateOptions) (network.CreateResponse, error)
	NetworkInspect(ctx context.Context, networkID string, options network.InspectOptions) (network.Inspect, error)
	NetworkRemove(ctx context.Context, networkID string) error
	NetworkConnect(ctx context.Context, networkID, containerID string, config *network.EndpointSettings) error

	ImageList(ctx context.Context, options image.ListOptions) ([]image.Summary, error)
	ImagePull(ctx context.Context, ref string, options image.PullOptions) (io.ReadCloser, error)

	ContainerCreate(ctx context.Context, config *container.Config, hostConfig *container.HostConfig, networkingConfig *network.NetworkingConfig, platform *ocispec.Platform, containerName string) (container.CreateResponse, error)
	ContainerStart(ctx context.Context, containerID string, options container.StartOptions) error
	ContainerStop(ctx context.Context, containerID string, options container.StopOptions) error
	ContainerRemove(ctx context.Context, containerID string, options container.RemoveOptions) error
	ContainerInspect(ctx context.Context, containerID string) (container.InspectResponse, error)
}

// the real SDK client satisfies Docker without an adapter
var _ Docker = (*dockerclient.Client)(nil)
```

A provider is typed on the block's Go type, so every method receives a
`*Network` with all its references already resolved. `Create` asks Docker
for a bridge network named after the block, labelled so the objects the
example made can be found with `docker network ls`, and records the ID Docker
gives it in the computed `DockerID`. `Destroy` removes the network by that
ID. Change detection comes from the embedded `DefaultChanged`.

Each method logs through `plugins.Logger(ctx)`, the logger xcl puts in the
call's context. It is already bound to the resource, its type, its file and
the step, so the provider passes only what it has to say. That works the same
inside the plugin process as it does in-process: the host gives each message
its call's resource and step.

```go title="example/plugin/plugins/docker/resources/network.go"
// Create asks Docker for a labelled bridge network named after the block, and
// records the ID Docker gives it
func (p *networkProvider) Create(ctx context.Context, n *Network) (*Network, error) {
	options := network.CreateOptions{
		Driver:     "bridge",
		Attachable: true,
		Labels:     labels(n.Meta),
	}

	if n.Subnet != "" {
		options.IPAM = &network.IPAM{
			Driver: "default",
			Config: []network.IPAMConfig{{Subnet: n.Subnet}},
		}
	}

	resp, err := p.client.NetworkCreate(ctx, n.Meta.Name, options)
	if err != nil {
		return nil, fmt.Errorf("unable to create network %s: %w", n.Meta.Name, err)
	}

	n.DockerID = resp.ID
	plugins.Logger(ctx).Info("created network", "name", n.Meta.Name, "id", n.DockerID)

	return n, nil
}

// Destroy removes the network, a network that is already gone counts as
// removed
func (p *networkProvider) Destroy(ctx context.Context, n *Network, force bool) error {
	err := p.client.NetworkRemove(ctx, n.DockerID)
	if err != nil && !dockerclient.IsErrNotFound(err) {
		return fmt.Errorf("unable to remove network %s: %w", n.Meta.Name, err)
	}

	plugins.Logger(ctx).Info("destroyed network", "name", n.Meta.Name, "id", n.DockerID)

	return nil
}
```

The container provider's `Create` does more. It pulls the image when Docker
does not have it, creates the container on its first network, then starts it
and inspects it for its address. The two computed fields are only set once
everything has worked, and a container that was created but failed to start
is removed again, so a failed `Create` leaves nothing behind:

```go title="example/plugin/plugins/docker/resources/container.go"
// Create pulls the image when Docker does not have it, creates the container
// on its first network, connects the rest, starts it and records its ID and
// its address on the first network. When a step after the container was
// created fails, the container is removed again.
func (p *containerProvider) Create(ctx context.Context, c *Container) (*Container, error) {
	err := p.pullImage(ctx, c.Image)
	if err != nil {
		return nil, err
	}

	config := &container.Config{
		Image:  c.Image,
		Cmd:    c.Command,
		Env:    environment(c.Environment),
		Labels: labels(c.Meta),
	}

	networking := &network.NetworkingConfig{}
	if len(c.Networks) > 0 {
		first := c.Networks[0]
		networking.EndpointsConfig = map[string]*network.EndpointSettings{
			first.Name: {Aliases: first.Aliases},
		}
	}

	resp, err := p.client.ContainerCreate(ctx, config, &container.HostConfig{}, networking, nil, c.Meta.Name)
	if err != nil {
		return nil, fmt.Errorf("unable to create container %s: %w", c.Meta.Name, err)
	}

	address, err := p.startContainer(ctx, c, resp.ID)
	if err != nil {
		removeErr := p.client.ContainerRemove(ctx, resp.ID, container.RemoveOptions{Force: true})
		return nil, errors.Join(err, removeErr)
	}

	c.DockerID = resp.ID
	c.IPAddress = address
	plugins.Logger(ctx).Info("created container", "name", c.Meta.Name, "image", c.Image, "ip_address", c.IPAddress)

	return c, nil
}
```

`startContainer` connects any further networks, starts the container and
reads its address on the first network back from `ContainerInspect`:

```go title="example/plugin/plugins/docker/resources/container.go"
// startContainer connects the created container to its further networks,
// starts it and returns its address on its first network
func (p *containerProvider) startContainer(ctx context.Context, c *Container, id string) (string, error) {
	for _, attachment := range c.Networks[min(1, len(c.Networks)):] {
		err := p.client.NetworkConnect(ctx, attachment.Name, id, &network.EndpointSettings{Aliases: attachment.Aliases})
		if err != nil {
			return "", fmt.Errorf("unable to connect container %s to network %s: %w", c.Meta.Name, attachment.Name, err)
		}
	}

	err := p.client.ContainerStart(ctx, id, container.StartOptions{})
	if err != nil {
		return "", fmt.Errorf("unable to start container %s: %w", c.Meta.Name, err)
	}

	inspect, err := p.client.ContainerInspect(ctx, id)
	if err != nil {
		return "", fmt.Errorf("unable to inspect container %s: %w", c.Meta.Name, err)
	}

	return firstAddress(c, inspect), nil
}
```

### The external binary

The Docker plugin is ordinary Go, written against the same `plugins` package
an in-process plugin uses. What makes it external is that it is a program of
its own: `example/plugin/plugins/docker` is its `main` package, holding the
plugin and a `main` that hands it to `plugins.Serve`, with the block types and
providers in `plugins/docker/resources` and the Docker client in
`plugins/docker/client`. The host program imports only
`plugins/docker/resources`, to read the blocks it applied. xcl does the rest:
the handshake with the host that started the process and the gRPC transport,
so the plugin never imports go-plugin. `make build` compiles it to
`build/docker-plugin`:

```go title="example/plugin/plugins/docker/main.go"
// main serves the plugin to the host that started this process
func main() {
	plugins.Serve(&Plugin{})
}
```

## The template plugin

The template plugin is compiled into the program. Its block type has no
subtype: `Init` registers `template` with an empty subtype, so a block is
written `template "welcome" {}`, with just a name, and addressed
`template.welcome`. xcl names an in-process plugin after its Go type, so its
log lines come from `TemplatePlugin`.

```go title="example/plugin/plugins/template/plugin.go"
// Init registers template with no subtype, so a block is written
// template "<name>" {} and addressed template.<name>
func (p *TemplatePlugin) Init(logger logger.Logger, state plugins.State) error {
	logger.Debug("registering block types", "block_types", "template")

	return plugins.RegisterResourceProvider(
		&p.PluginBase,
		logger,
		state,
		"template",
		"",
		&Template{},
		&provider{},
	)
}
```

By the time the provider's `Create` is called, every variable is resolved,
including the address the Docker plugin computed in another process. It
renders the template and writes the file, and its `Destroy` removes the file
again:

```go title="example/plugin/plugins/template/template.go"
// Create renders the template with its variables and writes the result to the
// destination
func (p *provider) Create(ctx context.Context, t *Template) (*Template, error) {
	err := render(t)
	if err != nil {
		return nil, err
	}

	plugins.Logger(ctx).Info("rendered template", "destination", t.Destination)

	return t, nil
}
```

`render` parses the source with the Handlebars library xcl's own template
function uses, with the same `quote` and `trim` helpers, and executes it with
the block's variables:

```go title="example/plugin/plugins/template/template.go"
// render renders t's source with its variables and writes it to its
// destination, creating the destination's parent directories
func render(t *Template) error {
	tmpl, err := raymond.Parse(t.Source)
	if err != nil {
		return fmt.Errorf("unable to parse template: %w", err)
	}

	// the helpers are the ones xcl's template function offers. They return
	// SafeString because Handlebars HTML-escapes what a helper returns
	// otherwise, which would write &quot; for the quotes quote adds.
	tmpl.RegisterHelpers(map[string]any{
		"quote": func(in string) raymond.SafeString {
			return raymond.SafeString(fmt.Sprintf(`"%s"`, in))
		},
		"trim": func(in string) raymond.SafeString {
			return raymond.SafeString(strings.TrimSpace(in))
		},
	})

	out, err := tmpl.Exec(t.Variables)
	if err != nil {
		return fmt.Errorf("unable to render template: %w", err)
	}

	err = os.MkdirAll(filepath.Dir(t.Destination), 0755)
	if err != nil {
		return fmt.Errorf("unable to create the directory for %s: %w", t.Destination, err)
	}

	err = os.WriteFile(t.Destination, []byte(out), 0644)
	if err != nil {
		return fmt.Errorf("unable to write %s: %w", t.Destination, err)
	}

	return nil
}
```

## The program

The program is `xcl-docker`, a command line tool built on xcl the way a real
one would be. It has four commands, and each is a separate run of the
program:

- `xcl-docker apply <path>` applies the configuration at `path`.
- `xcl-docker status` prints what the saved state holds, as a tree.
- `xcl-docker inspect <address>` prints one resource from the saved state as
  configuration text.
- `xcl-docker destroy` removes everything in the saved state.

`apply` and `destroy` print nothing of their own: the events they write to
standard error end with the operation's success or error. `status` and
`inspect` print only their output.

The runs share nothing but the state, saved in `./.xcl-docker` unless
`--state` names another directory. `xcl-docker` finds the Docker plugin next
to its own executable, where `make build` puts it, unless `--plugin` names
another binary. The flags are parsed with the standard library's `flag`
package, and `main` passes the command to one function per command:

```go title="example/plugin/main.go"
	switch command {
	case "apply":
		if flags.NArg() != 1 {
			fmt.Fprint(stderr, "apply needs the path of the configuration to apply\n\n"+usage)
			return 2
		}

		err = applyCommand(stderr, flags.Arg(0), *dockerPlugin, *stateDir)
	case "status":
		err = statusCommand(stdout, *dockerPlugin, *stateDir)
	case "inspect":
		if flags.NArg() != 1 {
			fmt.Fprint(stderr, "inspect needs the address of the resource to inspect\n\n"+usage)
			return 2
		}

		err = inspectCommand(stdout, flags.Arg(0), *dockerPlugin, *stateDir)
	case "destroy":
		err = destroyCommand(stderr, *dockerPlugin, *stateDir)
	default:
		fmt.Fprintf(stderr, "unknown command %q\n\n%s", command, usage)
		return 2
	}
```

Every command builds its `Config` the same way. Plugins come from a
registry, and the example uses the local registry, which holds the plugins an
application supplies itself. Registering a plugin only records it.
`RegisterPlugin` takes an in-process plugin and `RegisterExternalPlugin` the
path to an external plugin binary, and neither starts or checks anything nor
returns an error. `xcl.WithRegistry` gives the registry to the `Config`. The
plugins load at the start of the first operation, once per `Config`, and each
brings its own block types with it, so nothing else needs declaring. The
state is kept in a file, which is how one run picks up what the last one
saved:

```go title="example/plugin/main.go"
func newConfig(handler xcl.EventHandler, dockerPlugin, stateDir string) (*xcl.Config, error) {
	// The local registry holds plugins the application supplies itself: the
	// in-process plugin, which provides every block type it registers in
	// Init, and the external plugin binary. Registering only records a
	// plugin, each is loaded, and the binary started, by the first operation
	// that needs plugins.
	local := registry.NewLocal()
	local.RegisterPlugin(&template.TemplatePlugin{})
	local.RegisterExternalPlugin(dockerPlugin)

	return xcl.NewConfig(
		xcl.WithRegistry(local),
		// Keep the state in a file, so each command, a separate run of the
		// program, works from what the last one saved
		xcl.WithStatePath(stateDir),
		xcl.WithEventHandler(handler),
		// events carry nothing by default, this asks for each resource as
		// state records it, which is what the receiver turns back into
		// configuration text
		xcl.WithEventData(xcl.EventDataProcessed),
	)
}
```

`handler` is the receiver for xcl's [events](/events/). Each command that
changes something passes it the example's pretty terminal receiver, writing
to standard error at the level in `XCL_LOG_LEVEL`, info by default:

```go title="example/plugin/main.go"
func eventHandler(out io.Writer) xcl.EventHandler {
	return prettylog.Handler(out, prettylog.LevelFromEnv())
}
```

The receiver needs nothing else from the program. Each event returns the
entity it carries with `Event.Entity()`, typed by the `Config` that delivered
it, which is how the receiver shows each resource's
[configuration](/configuration-text/) as it is created.

`apply` checks that a Docker engine answers before it applies anything, so a
missing engine is a clear error rather than a failed `Create`. Nothing stops
the Docker plugin: xcl starts its process for each operation and stops it
when the operation is done:

```go title="example/plugin/main.go"
func applyCommand(stderr io.Writer, configDir, dockerPlugin, stateDir string) error {
	// The Docker plugin creates real containers, check an engine answers
	// before applying anything
	if err := client.Ping(context.Background()); err != nil {
		return err
	}

	c, err := newConfig(eventHandler(stderr), dockerPlugin, stateDir)
	if err != nil {
		return err
	}

	return apply(c, configDir)
}
```

`status` applies nothing. `Load` reads the saved state into the `Config`
without the configuration and without calling a provider, so the lookups
answer from what `apply` saved. It loads the plugins first, because a saved
plugin type is read back through its plugin's schema, but it never contacts
Docker. It prints only the tree, so it gives xcl no event handler:

```go title="example/plugin/main.go"
func statusCommand(stdout io.Writer, dockerPlugin, stateDir string) error {
	c, err := newConfig(nil, dockerPlugin, stateDir)
	if err != nil {
		return err
	}

	if err := load(c); err != nil {
		return err
	}

	return status(stdout, c)
}
```

`status` draws the tree with [Lip Gloss](https://github.com/charmbracelet/lipgloss).
It reads the networks, containers and templates back from the `Config`.
Plugin types are held as types generated from the plugin's schema, and the
lookup copies them into the plugin's Go type, so reading them back looks the
same as it does without plugins. A type with no subtype is looked up by its
type alone:

```go title="example/plugin/status.go"
	// template has no subtype, so its address has one segment before the name
	templates, err := xcl.FindByType[template.Template](c, "template")
	if err != nil {
		return nil, err
	}
```

Each resource saved in state records what it links to in `Meta.Links`, every
reference in its configuration. `status` nests each resource under the one it
depends on that is furthest down the chain, so the template, which reads both
the network and the container, sits under the container. The colours come
from a renderer made for standard output, so they show only in a terminal.

`inspect` reads the state the same way, finds the resource by its address and
turns it back into configuration text with `EncodeEntity`. It asks for the
values the provider set, each marked, and for every reference as it was
written, so the text shows how the resource is wired to the others. In a
terminal it is syntax highlighted through `xcl.Highlight`:

```go title="example/plugin/inspect.go"
func inspect(out io.Writer, c *xcl.Config, address string) error {
	entity, err := c.FindResource(address)
	if errors.Is(err, xcl.ErrNotFound) {
		return fmt.Errorf("no resource %s in the saved state, xcl-docker status lists them", address)
	}
	if err != nil {
		return err
	}

	options := []xcl.EncodeOption{xcl.IncludeComputed(), xcl.ShowReferences()}

	// xcl never checks for a terminal, asking it for colour is the program's
	// decision. It is decided for out itself, so output to a file or a pipe
	// is plain text.
	if lipgloss.NewRenderer(out).ColorProfile() != termenv.Ascii {
		renderer, err := highlight.NewANSIRenderer()
		if err != nil {
			return err
		}

		options = append(options, xcl.Highlight(renderer))
	}

	text, err := xcl.EncodeEntity(entity, options...)
	if err != nil {
		return err
	}

	_, err = out.Write(text)

	return err
}
```

`destroy` needs no configuration either. `Destroy` works from the saved
state alone and calls each provider's `Destroy`, dependents before what they
depend on:

```go title="example/plugin/main.go"
func destroyCommand(stderr io.Writer, dockerPlugin, stateDir string) error {
	if err := client.Ping(context.Background()); err != nil {
		return err
	}

	c, err := newConfig(eventHandler(stderr), dockerPlugin, stateDir)
	if err != nil {
		return err
	}

	return destroy(c)
}
```

A registered plugin that fails to load, such as a binary that was never
built, fails the operation with an error matching `xcl.ErrPluginLoad`, which
the example turns into a hint:

```go title="example/plugin/main.go"
func explainPluginLoad(err error) error {
	if errors.Is(err, xcl.ErrPluginLoad) {
		return fmt.Errorf("%w, build it with `make build` in example/plugin", err)
	}

	return err
}
```

## Testing

The providers are unit tested without Docker. Each test hands the provider
a `MockDocker`, the Mockery mock of the `client.Docker` interface, sets the
calls it expects, and checks what the provider did with the answer:

```go title="example/plugin/plugins/docker/resources/network_test.go"
func TestNetworkCreateFillsTheDockerID(t *testing.T) {
	client := mocks.NewMockDocker(t)
	client.EXPECT().
		NetworkCreate(context.Background(), "app", network.CreateOptions{
			Driver:     "bridge",
			Attachable: true,
			Labels: map[string]string{
				"created_by": "xcl-example-plugin",
				"xcl_id":     "docker.network.app",
			},
		}).
		Return(network.CreateResponse{ID: "net-123"}, nil).
		Once()

	provider := &networkProvider{client: client}

	created, err := provider.Create(context.Background(), testNetwork())

	require.NoError(t, err)
	require.Equal(t, "net-123", created.DockerID)
}
```

The mock lives in `plugins/docker/client/mocks` and is generated, not written:
after a change to `client.Docker`, `make generate` regenerates it with the
Mockery release pinned in the `Makefile`.

The tests that need a real engine, those that run the providers against
Docker and the end to end test of the program, call `client.Ping` first and
skip when no engine answers, so `make test` passes on a machine without
Docker:

```go title="example/plugin/plugins/docker/resources/docker_test.go"
// requireDocker skips the test when no Docker engine is reachable
func requireDocker(t *testing.T) {
	t.Helper()

	if err := client.Ping(context.Background()); err != nil {
		t.Skip(err.Error()) // Ping already says no Docker engine is reachable
	}
}
```

## Run it

From the `example/plugin` directory, with a Docker engine running, `make run`
builds `xcl-docker` and the Docker plugin side by side into `build/`, then
runs the three commands one after another:

```bash
make run
```

which is the same as:

```bash
make build
./build/xcl-docker apply ./config
./build/xcl-docker status
./build/xcl-docker destroy
```

## What to notice

- **Computed values flow between plugins.** The Docker plugin sets
  `ip_address` in its own process, and the in-process template provider
  receives it already resolved in its variables, because `template.welcome`
  references the container and so is always created after it.
- **A block type does not need a subtype.** `template` is registered with an
  empty subtype, so it is written `template "welcome" {}`, addressed
  `template.welcome` and looked up with `FindByType` by its type alone.
- **In-process and external look the same.** Both plugins are written
  against the same `plugins` package and log through the same
  `plugins.Logger(ctx)`. Only how they are registered, and the one line
  `main` that hands the external one to `plugins.Serve`, differ.
- **Each command is its own run, sharing only the state.** `apply` saves
  the state, `status` reads it back with `Load`, and `destroy` works from it
  alone, none of them needing what an earlier run held in memory.
- **Plugins load when first needed.** Registering only records a plugin. It
  is started and checked by the first operation, and a plugin that fails to
  load, such as a Docker plugin binary that was never built, fails it with
  `xcl.ErrPluginLoad`. The Docker plugin's process runs only while an
  operation uses it, so the program never stops it.
- **Destroy calls the providers in reverse dependency order.** `Destroy`
  works from the saved state alone, and removes the template before the
  container and the container before its network, the reverse of the order
  they were created in.
- **The tests run without Docker.** The providers hold a narrow `client.Docker`
  interface, so their unit tests use a generated mock, and the tests that
  need a real engine skip when `client.Ping` finds none.
