<Prose>

A library that prints is a library you have to fight. xcl never writes to
standard output or standard error, and never touches the standard library's
global logger. Instead, everything it and its plugins report, each step of
the entity lifecycle, plugin discovery and loading, warnings, errors and
the messages plugins log, is one stream of events delivered to the receiver
set with `xcl.WithEventHandler`. With no receiver, xcl is silent.

## Connecting to slog in one line

xcl ships an adapter to the standard library's `log/slog`, so the quickest
way to see the stream is one option:

<CodeTabs>
  <div slot="go">

```go title="main.go"
c, err := xcl.NewConfig(
	xcl.WithEventHandler(events.SlogHandler(slog.Default())),
)
if err != nil {
	return err
}
```

  </div>
  <div slot="python">

Python has no slog, so `xcl.logging_handler` writes through the standard
library's `logging` module instead:

```python title="main.py"
import logging

import xcl

cfg = xcl.Config(on_event=xcl.logging_handler(logging.getLogger("xcl")))
```

  </div>
</CodeTabs>

In Python the handler is any callable taking an `xcl.Event`, passed as
`on_event`; `xcl.aio.Config` accepts an `async def` handler as well, see the
<a href={pythonRepoURL}>Python package</a>.

`events.SlogHandler` takes any `*slog.Logger`, so the stream goes wherever
the rest of your program's logs go, in whatever format its handler writes.
Log messages are written at their own level, with their own text. Lifecycle,
discovery and load events are written at info, as `<operation> <phase>`,
failures at error, and a blocked announcement at warn. Filtering is left to
the slog handler's level, so a logger at info writes no debug messages.

Each event's fields become the attributes `source`, `operation`, `phase`,
`resource`, `type`, `file`, `duration` and `error`, when they are set,
followed by its details in key order.

`xcl.logging_handler` writes the same levels, messages and attributes as
`events.SlogHandler`, on standard `logging` records: debug, info, warning and
error, the same `<operation> <phase>` messages, and the same attribute names,
so a JSON or key-value formatter, structlog through its `ProcessorFormatter`
and loguru through its standard logging integration see them as fields. Each
record also carries the event's time, and `record.xcl_event` is the
`xcl.Event` itself. The logger's level is checked first, so a filtered event
costs one call. With no logger, it writes to `logging.getLogger("xcl")`.

### Errors in logs

`events.SlogHandler` writes an event's error as its one-line message, so a
configuration problem is logged as one line, with its file, range, summary,
detail, block and field. Other loggers can carry the full
[report](/problems/#showing-problems-to-a-person) a person reads: zap's
`zap.Error(err)` writes it in its `errorVerbose` field, with no adapter.
`xcl.logging_handler` writes an event's error as the same one line, and in
Python the error an operation raises carries the report as an exception
note, so `logger.exception(...)` writes it under the traceback, and
`xcl.highlight.LogFormatter` writes it in colour; see
[In logs](/problems/#in-logs).

To show the report under the log line, a receiver can print the event's
`Error` with `xcl.PrintError`, or `event.error` with `xcl.print_error` in
Python. Each configuration problem has an error event of its own carrying the
`*xclerrors.Diagnostic`, and the event that ends the call carries the
`*xclerrors.ConfigError` holding them all, so this receiver prints each
problem once, under its own line. In Python each problem's event carries an
`xcl.ConfigError` holding that problem alone, and the one that ends the call
carries the `xcl.ConfigError` whose `causes` are all of them:

<CodeTabs>
  <div slot="go">

```go title="main.go"
import (
	"log/slog"
	"os"

	"github.com/jumppad-labs/xcl"
	xclerrors "github.com/jumppad-labs/xcl/errors"
	"github.com/jumppad-labs/xcl/events"
	"github.com/jumppad-labs/xcl/highlight"
)

logEvent := events.SlogHandler(slog.Default())

c, err := xcl.NewConfig(
	xcl.WithEventHandler(func(e xcl.Event) {
		logEvent(e)

		if problem, ok := e.Error.(*xclerrors.Diagnostic); ok {
			xcl.PrintError(os.Stderr, problem, xcl.WithFormatter(highlight.For(os.Stderr)))
		}
	}),
)
```

  </div>
  <div slot="python">

```python title="main.py"
import logging
import sys

import xcl

log_event = xcl.logging_handler(logging.getLogger("app"))


def on_event(event: xcl.Event) -> None:
    log_event(event)

    # one problem's error collects no others; the error that ends the call
    # collects them all as its causes
    if event.error is not None and event.error.tokens and not event.error.causes:
        xcl.print_error(event.error, formatter=xcl.highlight.for_stream(sys.stderr))


cfg = xcl.Config(on_event=on_event)
```

  </div>
</CodeTabs>

## The event

Every event is an `xcl.Event`, an alias of `events.Event`. There is one flat
shape for all of them, whether it is xcl creating an entity or a plugin
logging a message:

| Field | Meaning |
|---|---|
| `Time` | when it happened |
| `Source` | `core` for xcl itself, otherwise the name of the plugin it came from |
| `Operation` | the operation or step the event belongs to |
| `Phase` | where in that operation it is |
| `ResourceType`, `ResourceID`, `File` | the entity the event is about, and the file it was declared in |
| `Duration` | how long a step took, or how long emitting was blocked |
| `Error` | the failure, for the `error` phase |
| `Data` | the serialized entity, for lifecycle events only |
| `Meta` | the details, keyed by name |

A log message's level and text are in `Meta`, under the reserved keys
`events.KeyLevel` (`level`) and `events.KeyMessage` (`message`). The level is
one of `debug`, `info`, `warn` or `error`. The details a caller passes with a
message are the other keys, under their own names, and never overwrite the
reserved two.

To handle events yourself, `EventHandler` is a function that takes an event:

<CodeTabs>
  <div slot="go">

```go title="main.go"
var failures []error

c, err := xcl.NewConfig(
	xcl.WithEventHandler(func(e xcl.Event) {
		if e.Phase == events.PhaseError {
			failures = append(failures, e.Error)
		}
	}),
)
if err != nil {
	return err
}
```

  </div>
  <div slot="python">

```python title="main.py"
failures: list[xcl.Error] = []


def handler(event: xcl.Event) -> None:
    if event.phase == "error":
        failures.append(event.error)


cfg = xcl.Config(on_event=handler)
```

  </div>
</CodeTabs>

The Python `xcl.Event` carries the same fields as `time`, `source`,
`operation`, `phase`, `resource_type`, `resource_id`, `file`, `duration`,
`error`, `data` and `meta`, with a log message's level and text as
`event.level` and `event.message`.

## Sensitive values in event data

Lifecycle events carry entity data only when you ask for it with
`xcl.WithEventData`. When they do, every sensitive value in `Data` is written
through the event masker. The default is `mask.Redact()`, which shows the
marker inside an envelope naming the masker that produced it:

```json
"password": {"xcl_masked": "redact", "value": "(sensitive)"}
```

Choose another masker with `xcl.WithEventMask`. A keyed hash lets a receiver
tell whether two events carry the same value without ever seeing it:

<CodeTabs>
  <div slot="go">

```go title="main.go"
eventMask, err := mask.HashHMACSHA256(correlationKey)
if err != nil {
	return err
}

c, err := xcl.NewConfig(
	xcl.WithEventHandler(handler),
	xcl.WithEventData(xcl.EventDataProcessed),
	xcl.WithEventMask(eventMask),
)
```

  </div>
  <div slot="python">

```python title="main.py"
event_mask = xcl.mask.hmac_sha256(correlation_key)

cfg = xcl.Config(
    on_event=handler,
    event_data=xcl.EventDataLevel.PROCESSED,
    event_mask=event_mask,
)
```

  </div>
</CodeTabs>

Any masker works here, including the built-ins `mask.Omit()`, which writes no
value, `mask.EncryptAES256GCM(key)` and your own. When every receiver is
trusted with secrets, `xcl.WithNoEventMask()` turns masking off and event data
carries the real values. When both options are given, the last one wins. In
Python the options are `event_data=` with an `xcl.EventDataLevel` (`NONE`,
`RAW` or `PROCESSED`), `event_mask=` with one of the `xcl.mask` built-ins, and
`no_event_mask=True`.

Event masking changes only `Data`. Errors and log details always show
`(sensitive)`, whatever the event masker, because the sensitive type formats
itself as the marker. A receiver holding a reversible masker can open a masked
value with `mask.Unmask(data, m)`; anything it cannot open faithfully, such as
a hash, data from a different masker or data under a different key, fails with
`xcl.ErrUnrecoverable` and returns no value. `Event.Entity()` and
`c.EncodeSavedEntity`, `event.entity()` and `cfg.encode_saved_entity` in
Python, show every masked value as `(sensitive)`. In Python,
`cfg.encode_saved_entity(event.data)` turns the record an event carries into
configuration text at any time, from inside the handler while the operation
runs too. `cfg.encode_entity(event.entity())` does the same once the
operation has finished, and is refused with `xcl.OperationInProgressError`
while it runs; with `reveal_sensitive=True` it shows the engine's current
value, not the masked one.

To keep secrets out of the state file as well, see
[State masking](/state-masking/).

## Operations and phases

The operations and phases are defined as constants in the `events` package.

| Operation | What it covers |
|---|---|
| `validate`, `apply`, `destroy` | a whole call to `Validate`, `Apply` or `Destroy` |
| `load_state` | a whole call to `Load`, reading the saved state |
| `parse` | one block as it is read, with the file it came from |
| `create`, `read`, `changed`, `update`, `destroy` | one provider call for one entity |
| `discover` | searching the directories given to a local registry's `RegisterPluginDirectory` |
| `load` | starting and checking one plugin, and anything a plugin logs outside a provider call |
| `events` | the event stream itself, for a `blocked` announcement |

| Phase | Meaning |
|---|---|
| `start` | the operation or step is starting |
| `success` | it finished, with its `Duration` |
| `error` | it failed, with its `Error` |
| `log` | a log message, with its level and text in `Meta` |
| `blocked` | emitting had to wait for the receiver |

Each `Validate`, `Apply` and `Destroy` starts with its own `start` event and
ends with a `success`, or an `error` carrying the error it returns. In
between come the `load` events for any plugins loading, the `parse` events,
and for each entity a `start` before each provider call, then any messages
the provider logs during that call, with the call's step as their operation,
then the call's `success` or `error`. Every failure that is returned is also
emitted as an error event, including each problem validation finds.

This is how one entity looks through the example's receiver, the
[plugin example](/examples/plugins/) creating a Docker network:

```text
3:53PM INFO create start source=core operation=create phase=start resource=docker.network.app type=network.app file=config/full/main.xcl
3:53PM INFO created network source=docker-plugin operation=create phase=log resource=docker.network.app type=network.app file=config/full/main.xcl id=2f783968958bf8d9ee7914b98f809c0ced9b93509ad59946d0ff1f250f0c3764 name=app
3:53PM INFO create success source=core operation=create phase=success resource=docker.network.app type=network.app file=config/full/main.xcl duration=3.469262ms
```

## Sources

`Source` says who is reporting. It is `core`, `events.SourceCore`, for
everything xcl reports itself: the operations, parsing, loading and the
lifecycle steps. A message a plugin logs carries the plugin's name instead:
the Go type name of an in-process plugin, such as `TemplatePlugin`, or the
file name of an external plugin's binary, such as `docker-plugin`. The messages
go-plugin writes while it starts an external plugin carry that plugin's name
too, with the detail `component=go-plugin` so a receiver can tell them apart
from the plugin's own.

A plugin never sets these itself. How a plugin logs, and how its messages
get their entity and step, is covered in
[Plugin logging and loading](/plugin-logging/).

## Delivery guarantees

- **Ordered, one at a time.** The receiver is called with one event at a
  time, in the order the events were emitted, never concurrently, on the
  goroutine that called `Validate`, `Apply` or `Destroy`. It needs no locking
  of its own. Both Python clients deliver events the same way: `xcl.Config`
  calls `on_event` on the thread running the operation, and `xcl.aio.Config`
  calls it once per event, in order, each call finished before the next
  starts.
- **Never dropped.** Emitting never waits for the receiver. Undelivered
  events are held in a bounded buffer, set with `xcl.WithEventBufferSize`
  (default `xcl.DefaultEventBufferSize`, 1024). When the buffer is full,
  emitting waits for the receiver to catch up rather than dropping an event.
- **Blocking is announced.** Once emitting can continue after waiting, the
  receiver is sent one event with the operation `events` and the phase
  `blocked`, whose `Duration` says how long it waited. A receiver that sees
  these is slower than the work it is watching.
- **Delivered before return.** Every event of a call has been delivered
  before `Validate`, `Apply` or `Destroy` returns, whether it succeeds or
  fails.

```go title="main.go"
	xcl.WithEventHandler(handler),
	// hold more undelivered events before emitting waits

	return err
}
```

  </div>

## Errors and panics in the receiver

A receiver returns nothing, so it can not fail an operation, and the failures
an operation returns reach it as `error` events as well as the returned
error.

A panic in the receiver is not recovered. xcl starts no new provider call,
lets the calls already in progress finish, and saves state, so nothing that
was created is forgotten. Then the panic continues from `Validate`, `Apply`
or `Destroy` with its original value and stack.

## A pretty receiver

The examples share a receiver,
[`example/prettylog`](https://github.com/jumppad-labs/xcl/tree/main/example/prettylog),
which shows how little an application needs. It is `events.SlogHandler`
wrapped around a slog handler from
[charmbracelet/log](https://github.com/charmbracelet/log), chosen for its
readable, coloured terminal output. It is an example, not part of xcl, so it
never becomes a dependency of an application that uses xcl. Python ships the
same receiver as `xcl.prettylog`, part of the package and written with the
standard library alone, coloured by the package's own printing support, and
it writes the same lines.

<CodeTabs>
  <div slot="go">

```go title="example/prettylog/prettylog.go"
func Handler(w io.Writer, level slog.Level) xcl.EventHandler {
	logger := charmlog.NewWithOptions(w, charmlog.Options{
		Level:           charmlog.Level(level),
		ReportTimestamp: true,
		TimeFormat:      time.Kitchen,
	})

	logger.SetStyles(styles())

	delegate := events.SlogHandler(slog.New(logger))
	// ...
}
```

  </div>
  <div slot="python">

```python
import sys

import xcl

cfg = xcl.Config(
    on_event=xcl.prettylog.handler(sys.stderr, xcl.prettylog.level_from_env()),
    event_data=xcl.EventDataLevel.PROCESSED,
)
```

```text
3:04PM INFO create success source=core operation=create phase=success resource=resource.recording.one type=recording.one file=/work/main.xcl duration=509µs
  resource "recording" "one" {
    log    = "/work/log.jsonl"
    value  = "a"
    output = "one-a" # set by the provider
  }
```

</CodeTabs>

`xcl.aio.Config` takes the same handler, and
`xcl.prettylog.handler(logger=logging.getLogger("app"))` sends the same lines
through a standard logger instead of a stream.

It also writes the configuration of each entity it sees created beneath the
line reporting it. The event itself returns that entity, as the Go type
registered for its block type, with `Event.Entity()`, and the receiver turns
it back into configuration text with `xcl.PrintEntity`, values the provider
filled in included, so it needs nothing from the application but event data
at `xcl.EventDataProcessed`. Whether to colour is the logger's own decision,
made for its writer: when charmbracelet/log colours its lines, the
configuration is printed in the `highlight.Terminal` format, and otherwise as
plain text. xcl does the colouring, and the example only chooses the format:

```go title="example/prettylog/prettylog.go"
formatter := highlight.Plain
if lipgloss.NewRenderer(w).ColorProfile() != termenv.Ascii {
	formatter = highlight.Terminal
}

// for each entity created
xcl.PrintEntity(&text, entity, xcl.IncludeComputed(), xcl.WithFormatter(formatter))
```

The Python receiver renders each created resource from the event's saved
record, which the engine allows while the operation runs, and colours it
through `xcl.highlight` when the stream is a terminal and `NO_COLOR` is unset.
It also writes a configuration mistake's report, with the source lines in
question, beneath the line reporting the error, and says once how to turn
resource data on when it is off.

See [Printing and highlighting](/configuration-text/#printing-and-highlighting).

Every example sets it up in one line, writing to standard error at the level
named by `XCL_LOG_LEVEL`, one of `debug`, `info`, `warn` or `error`, and info
when it is unset:

## The one exception

xcl runs external plugins with HashiCorp's
[go-plugin](https://github.com/hashicorp/go-plugin), and one message escapes
the stream. When an external plugin is stopped within milliseconds of
starting, go-plugin v1.6.3 writes this to standard error through the standard
library's global logger:

```text
[ERR] plugin: plugin acceptAndServe error: broker closed
```

It is outside xcl's control, and xcl deliberately does not change the global
logger to hide it. The rest of what go-plugin reports reaches the stream as
log events with `component=go-plugin`: its info and debug messages at debug,
its warnings and errors at their own level.
