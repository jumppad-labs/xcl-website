Everything a configuration declares is an entity: a database, an app, a
variable, a module. Each is written as a block whose labels give its type and
name, and each has an address that other blocks, and the application, refer
to it by.

## Blocks and labels

```hcl title="main.xcl"
database "postgres" "main" {
  location = "db.local"
}

app "web" {
  image = "nginx:1.27"
}
```

The keyword before the labels is the entity's **type**: `database` and
`app`. The last label is its **name**: `main` and `web`. A type can take a
**subtype** between the two: `postgres` is the subtype of the first block.
The subtype is optional, but whether a block has one is not its own choice. It is fixed by how the
type was registered: a type registered with a subtype is always written with
one, and a type registered without one never takes one.

<CodeTabs>
  <div slot="go">

```go title="main.go"
local := registry.NewLocal()
registry.Register[PostgreSQL](local, "database", "postgres") // database "postgres" "main" {}
registry.Register[App](local, "app")                         // app "web" {}
```

  </div>
  <div slot="python">

```python title="resources.py"
@xcl.entity("database", "postgres")  # database "postgres" "main" {}
@dataclass
class PostgreSQL(xcl.Resource):
    location: str


@xcl.entity("app")                   # app "web" {}
@dataclass
class App(xcl.Resource):
    image: str
```

  </div>
</CodeTabs>

## Addresses

An entity's address is its labels joined with dots: `database.postgres.main`
and `app.web`. The address is what a reference starts with, so
`database.postgres.main.location` reads the first block's `location`, and it
is what the application passes to `xcl.Find[T]` or `cfg.find`.

An entity declared inside a module has the module's name in front:
`module.<name>.<address>`, such as `module.db.database.postgres.main`, and
one in a module nested in another module has both, `module.a.module.b.…`.
See [References and processing order](/language/references/) for what a
reference may reach.

## Built-in fields

Every entity has two attributes that can be written in configuration, and a
`meta` object that xcl fills in and configuration can only read:

```hcl title="main.xcl"
app "web" {
  image      = "nginx:1.27"
  depends_on = ["database.postgres.main"]
  disabled   = false
}
```

- `depends_on` lists the addresses of entities that must be processed before
  this one, for an order that no reference expresses.
- `disabled`, when `true`, leaves the entity out of processing.

The `meta` fields are read through another entity's address, so a block can
pass on an entity's identity rather than repeat it:

```hcl title="deployment.xcl"
deployment "api" {
  image      = "api:1.4"
  config_map = config_map.api.meta.id
}
```

```hcl title="main.xcl"
docker "container" "web" {
  image = "nginx:1.27-alpine"

  network {
    name = docker.network.main.meta.name
  }
}
```

| Field | Value |
|---|---|
| `meta.id` | the entity's address, such as `config_map.api` |
| `meta.name` | the name label, such as `api` |
| `meta.type` | the type keyword, such as `config_map` |
| `meta.subtype` | the subtype label, empty for a type without one |
| `meta.module` | the name of the module the entity was declared in, empty at the root |
| `meta.file` | the absolute path of the file the block is in |
| `meta.line` | the line the block starts on |
| `meta.column` | the column the block starts at |

In code these fields live on the base every entity type builds on. In Go it
is `types.ResourceBase`, embedded with the `xcl:",remain"` tag so that
`depends_on`, `disabled` and `meta` are decoded alongside the type's own
fields. A declared type can instead be a plain struct: xcl keeps the base for
it, and a field called `Meta`, a `types.Meta` with no tag, receives a copy of
the metadata, while fields tagged `disabled` or `depends_on` receive those
values. In Python it is `xcl.Resource`, which also gives the entity an
`address` property:

<CodeTabs>
  <div slot="go">

```go title="types/resource.go"
type ResourceBase struct {
	DependsOn []string `xcl:"depends_on,optional" json:"depends_on,omitempty"`
	Disabled  bool     `xcl:"disabled,optional" json:"disabled,omitempty"`
	Meta      Meta     `xcl:"meta,optional" json:"meta,omitempty"`
}
```

  </div>
  <div slot="python">

```python title="xcl/_entity.py"
@dataclass(kw_only=True)
class Resource:
    meta: Meta | None = None
    depends_on: list[str] = field(default_factory=list)
    disabled: bool = False
```

  </div>
</CodeTabs>

Reading them back from an entity the application has found:

<CodeTabs>
  <div slot="go">

```go title="main.go"
app, err := xcl.Find[App](c, "app.web")

	return err
}

fmt.Println(app.Meta.ID, app.Meta.File, app.Meta.Line)
```

```python title="main.py"
app = cfg.find(App, "app.web")

print(app.address)                              # app.web
print(app.meta.id, app.meta.file, app.meta.line)
print(app.depends_on, app.disabled)
```

## Entity types

The language itself declares three types: `variable`, `output` and
`module`. Every other type comes from the application that reads the
configuration, either a plain Go or Python type it registers, or a type a
plugin provides together with the provider that runs it. Both are given to a
`Config` through [registries](/registries/), and a configuration can only use
types the `Config` was given.
