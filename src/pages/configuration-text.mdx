<Prose>

Showing someone what a configuration holds is easiest in the syntax they
wrote it in. `xcl.EncodeEntity` turns one entity back into configuration text,
and the Config's `EncodeSavedEntity` does the same from its saved data. In
Python the two are `cfg.encode_entity` and `cfg.encode_saved_entity`, and the
engine renders the text, so Python and Go write identical text for the same
entity. Both write exactly one block, so convert several entities by calling
once for each. The text is plain, and `xcl.PrintEntity` in Go and
`cfg.print_entity` in Python print an entity coloured for a terminal, as HTML
or as SVG in one call.

## Converting an entity

Pass an entity as the configuration holds it, as `FindResource`, `Entities` and
`FindEntitiesByType` return it. A copy `Find[T]` returns is your own plain
struct, which does not say what it was declared as, and is refused:

<CodeTabs>
  <div slot="go">

```go title="main.go"
db, err := c.FindResource("database.postgres.main")
if err != nil {
	return err
}

text, err := xcl.EncodeEntity(db)
if err != nil {
	return err
}

fmt.Println(string(text))
```

  </div>
  <div slot="python">

```python title="main.py"
db = cfg.find(PostgreSQL, "database.postgres.main")

print(cfg.encode_entity(db))
```

With `xcl.aio.Config` the call is `await cfg.encode_entity(db)`. Any entity a lookup returns works, as does an instance of a registered class you built yourself, and the `xcl.Entity` a lookup returns for a plugin's type. A field you change on a looked-up entity shows in the text.

  </div>
</CodeTabs>

```hcl
database "postgres" "main" {
  location = "localhost"
  port     = 5432

  timeouts {
    connection = 10
    keep_alive = 60
  }
}
```

The text shows what a person wrote. xcl's own bookkeeping is not written, and
neither is `depends_on`. A `variable`, `output` or `module` is never written as
configuration, and asking for one fails with `xcl.ErrNotEncodable`.

## Converting saved data

`c.EncodeSavedEntity` takes an entity's saved data, in the form state stores it
and events carry it at `xcl.EventDataProcessed`. The record's type is resolved
through the Config, from the Go types its registries declare and the types
its plugins provide, and its plugins are loaded if they are not loaded already:

<CodeTabs>
  <div slot="go">

```go
text, err := c.EncodeSavedEntity(event.Data)
```

  </div>
  <div slot="python">

```python
text = cfg.encode_saved_entity(event.data)
```

It takes the same keyword choices as `cfg.encode_entity`, such as `cfg.encode_saved_entity(event.data, include_computed=True)`. Here `event` is the `xcl.Event` an `on_event` handler receives, and `event.data` holds the saved record when the Config was created with `event_data=xcl.EventDataLevel.PROCESSED`. With `xcl.aio.Config` the call is `await cfg.encode_saved_entity(event.data)`.

  </div>
</CodeTabs>

A saved record can be rendered at any time, including from an event handler
while an operation is still running, because rendering it reads none of the
Config's entities. That is how a program shows each resource as it is
created, beneath its success event, rather than all at the end. The text is
the same as the same call gives once the operation has finished:

<CodeTabs>
  <div slot="go">

```go
handler := func(e xcl.Event) {
	if e.Operation == "create" && e.Phase == "success" {
		text, err := c.EncodeSavedEntity(e.Data)
		if err == nil {
			fmt.Println(string(text))
		}
	}
}
```

  </div>
  <div slot="python">

```python
def on_event(event):
    if event.operation == "create" and event.phase == "success":
        print(cfg.encode_saved_entity(event.data, include_computed=True))
```

Rendering a looked-up or edited entity with `cfg.encode_entity` is refused
while an operation runs, from an event handler too, with
`xcl.OperationInProgressError`: it reads the engine's own copy of the entity,
which the operation is still changing. Render the event's saved record with
`cfg.encode_saved_entity(event.data)` instead.

  </div>
</CodeTabs>

Variables and outputs have create success events too. Their records are not
configuration, so rendering one fails with `xcl.ErrNotEncodable`.

The text is identical to what `EncodeEntity` returns for the same entity. A
record naming a type the Config does not know fails with
`xcl.ErrUnregisteredType`, data that is not one saved record with
`xcl.ErrInvalidSavedData`, and a plugin that fails to load with
`xcl.ErrPluginLoad`.

An event receiver does not need the Config at all. `Event.Entity()` returns
the entity an event carries, as the Go type registered for its block type and
with every sensitive value masked, ready for `EncodeEntity`. It returns nil
when the event carries no data:

<CodeTabs>
  <div slot="go">

```go
entity, err := e.Entity()
if err != nil || entity == nil {
	return
}

text, err := xcl.EncodeEntity(entity)
```

  </div>
  <div slot="python">

```python
entity = event.entity()
if entity is None:
    return

text = cfg.encode_entity(entity)
```

`cfg.encode_entity(entity)` works once the operation has finished: while it is running, from inside the handler too, it raises `xcl.OperationInProgressError`. From inside the handler, `cfg.encode_saved_entity(event.data)` gives the same text. An event entity kept and encoded after its operation has finished shows the engine's current value with `reveal_sensitive=True`, where Go's event data always shows the marker.

  </div>
</CodeTabs>

## Provider-filled values

Values a provider filled in, such as an address or an id it assigned, are left
out by default. Ask for them with `xcl.IncludeComputed()`, and each one is
marked so a reader can tell it apart:

<CodeTabs>
  <div slot="go">

```go
text, err := xcl.EncodeEntity(db, xcl.IncludeComputed())
```

  </div>
  <div slot="python">

```python
text = cfg.encode_entity(db, include_computed=True)
```

  </div>
</CodeTabs>

```hcl
database "postgres" "main" {
  location          = "localhost"
  port              = 5432
  connection_string = "postgres://admin@localhost:5432/main" # set by the provider
}
```

## Empty attributes

An optional attribute left unset, or set to its zero value, is left out by
default. Ask for `xcl.IncludeEmpty()` and each one is written with the empty
value of its type: `""` for a string, `[]` for a list, `{}` for a map, and
the zero value of the type a nullable attribute holds:

<CodeTabs>
  <div slot="go">

```go
text, err := xcl.EncodeEntity(db, xcl.IncludeEmpty())
```

  </div>
  <div slot="python">

```python
text = cfg.encode_entity(db, include_empty=True)
```

  </div>
</CodeTabs>

## Sensitive values

A sensitive value is written as the marker `"(sensitive)"`. Pass
`xcl.RevealSensitive()` to write the real value. Event data carries the marker
rather than the value, so text made from event data shows the marker even when
revealing is asked for. See [Sensitive values](/sensitive-values/) for
declaring a field sensitive.

<CodeTabs>
  <div slot="go">

```go
text, err := xcl.EncodeEntity(db, xcl.RevealSensitive())
```

  </div>
  <div slot="python">

```python
text = cfg.encode_entity(db, reveal_sensitive=True)
```

A looked-up entity holds only the marker, so the engine writes its own configured value. A value the entity holds for real, such as one you changed or one set on an instance you built yourself, is written as it is. An event entity kept until after its operation shows the engine's current value, unlike Go's event data.

  </div>
</CodeTabs>

## Dependency lists

A `depends_on` list is written exactly as you wrote it, and left out when you
wrote none. The dependencies xcl works out from references are never added to
it, though they still order creation and destruction. Given this
configuration:

```hcl
app "c" {
  y = "blue"
}

app "a" {
  depends_on = ["app.b"]

  x = app.c.y
}
```

the text for `app.a` names only the dependency you wrote, while the
reference to `app.c` comes out as the value it resolved to:

```hcl
app "a" {
  depends_on = ["app.b"]

  x = "blue"
}
```

The list is the same after the configuration is applied and when it is loaded
back from saved state, so text from a live entity and from its saved data
matches.

## Showing references as written

By default a field that referred to another entity shows the value it resolved
to. Ask for `xcl.ShowReferences()` and each such field is written exactly as the
user wrote it instead, whether a bare reference, a template or a reference in a
nested block. Given this configuration:

```hcl
app "web" {
  db_location = database.postgres.main.location
  url         = "https://${database.postgres.main.location}/app"
}
```

<CodeTabs>
  <div slot="go">

```go
text, err := xcl.EncodeEntity(app, xcl.ShowReferences())
```

  </div>
  <div slot="python">

```python
text = cfg.encode_entity(app, show_references=True)
```

An instance you built yourself has no references, so its values are written as they are.

  </div>
</CodeTabs>

the text shows each reference as it was written:

```hcl
app "web" {
  db_location = database.postgres.main.location
  url         = "https://${database.postgres.main.location}/app"
}
```

Without the option the same entity is written with its resolved values:

```hcl
app "web" {
  db_location = "localhost"
  url         = "https://localhost/app"
}
```

It works the same from saved data,
`c.EncodeSavedEntity(record, xcl.ShowReferences())`, and the two
give byte-identical text, since the references are kept in each entity's saved
record. It combines with `xcl.IncludeComputed()`.

A sensitive field shows its reference only when it was written as a single bare
reference, such as `password = variable.db_password`, since an address holds no
secret. Written any other way it keeps `"(sensitive)"`, unless
`xcl.RevealSensitive()` is also given. State saved by an earlier version of xcl
holds no references, so its text shows resolved values until the configuration
is applied again.

## Printing and highlighting

`xcl.EncodeEntity` always gives plain text. `xcl.PrintEntity` writes the same
text to an `io.Writer` in one call, plain, coloured for a terminal, or as HTML
or SVG, so the configuration in your terminal or your page looks the way it
does in the editor. It takes the encoding choices on this page in the same
list as the printing options, so `xcl.IncludeComputed()` sits beside
`xcl.WithFormatter(...)`:

<CodeTabs>
  <div slot="go">

```go title="main.go"
import (
	"os"

	"github.com/jumppad-labs/xcl"
	"github.com/jumppad-labs/xcl/highlight"
)

db, err := c.FindResource("database.postgres.main")
if err != nil {
	return err
}

err = xcl.PrintEntity(os.Stdout, db,
	xcl.IncludeComputed(),
	xcl.WithFormatter(highlight.For(os.Stdout)),
)
```

  </div>
  <div slot="python">

```python title="main.py"
import sys

import xcl

db = cfg.find(PostgreSQL, "database.postgres.main")

cfg.print_entity(db,
    include_computed=True,
    formatter=xcl.highlight.for_stream(sys.stdout),
)
```

`cfg.print_entity` writes to `sys.stdout` unless you pass a stream as its second argument, and takes the encoding keywords on this page beside the printing keywords `formatter=` and `theme=`. `cfg.print_saved_entity(event.data, include_computed=True)` prints a saved record the same way, from an `on_event` handler while an operation runs too, as `cfg.encode_saved_entity` does. Both raise what the encode calls raise, writing nothing. With `xcl.aio.Config` the calls are awaited, such as `await cfg.print_entity(db)`.

  </div>
</CodeTabs>

The printing options are `xcl.WithFormatter`, which picks the format and
defaults to `highlight.Plain`, and `xcl.WithTheme`, which picks the colours
and defaults to `highlight.DefaultTheme`. `PrintEntity` fails with
`xcl.ErrNotEncodable`, writing nothing, wherever `EncodeEntity` would, and
otherwise returns the first error writing to `w`. Highlighting works on the
text every encoding choice produces, including `xcl.ShowReferences()`, whose
references are coloured as references. `xcl.PrintError` and `xcl.PrintDiff`
take the same options for [an error report](/problems/) and
[a change summary](/diff/).

### Output formats

A format is a `highlight.Formatter`, and the `highlight` package ships five:

| Formatter | Writes |
| --- | --- |
| `highlight.Plain` | the text exactly as `EncodeEntity` returns it, ignoring the theme |
| `highlight.Terminal` | the text in terminal colour codes from the theme |
| `highlight.HTML` | a `<pre class="xcl">` block with a class on each piece of text, for a website to style |
| `highlight.HTMLInline` | the same markup styled with `style` attributes, for places a stylesheet cannot reach, such as an email |
| `highlight.SVG` | a standalone SVG image that carries its own colours |

<CodeTabs>
  <div slot="go">

```go
file, err := os.Create("database.svg")
if err != nil {
	return err
}
defer file.Close()

err = xcl.PrintEntity(file, db, xcl.WithFormatter(highlight.SVG))
```

  </div>
  <div slot="python">

```python
import xcl

with open("database.svg", "w", encoding="utf-8") as file:
    cfg.print_entity(db, file, formatter=xcl.highlight.SVG)
```

The five formats are `xcl.highlight.PLAIN`, the default, `TERMINAL`, `HTML`, `HTML_INLINE` and `SVG`, and each writes the same bytes as Go's.

  </div>
</CodeTabs>

`highlight.Terminal` writes the 16 named colours as the terminal's own
palette, so the default theme follows the user's colours, and a `#rrggbb`
colour as 24-bit colour. Text styled with nothing gets no colour codes at
all. Every line is styled on its own, with a reset before each line break, so
the text can be indented or prefixed line by line without colour leaking.
Removing the colour codes gives back exactly the plain text.

xcl never decides on its own whether to colour output: the default is plain
text. `highlight.For(w)` makes the usual choice when you ask it to. It returns
`highlight.Terminal` when `w` is a terminal, an `*os.File` that is a
character device, and the `NO_COLOR` environment variable is unset or empty,
and `highlight.Plain` for anything else, such as a file, a pipe or a buffer. A
program that already decides colour, such as through its logging library,
passes the formatter itself:

<CodeTabs>
  <div slot="go">

```go
formatter := highlight.Plain
if colour {
	formatter = highlight.Terminal
}

err = xcl.PrintEntity(os.Stdout, db, xcl.WithFormatter(formatter))
```

  </div>
  <div slot="python">

```python
import xcl

formatter = xcl.highlight.PLAIN
if colour:
    formatter = xcl.highlight.TERMINAL

cfg.print_entity(db, formatter=formatter)
```

`xcl.highlight.for_stream(stream)` makes the same choice as `highlight.For`: `TERMINAL` when `stream.isatty()` is true and `NO_COLOR` is unset or empty, and `PLAIN` for anything else, such as a file, a pipe or a `StringIO`.

  </div>
</CodeTabs>

Here `colour` is your application's own decision. The
[logging example](https://github.com/jumppad-labs/xcl/tree/main/example/prettylog)
makes it for its writer before asking for colour.

### Themes

A `highlight.Theme` says how each kind of text looks, as a short style string
for each `highlight.Kind` it styles, such as `highlight.Attribute` or
`highlight.LineComment`. A style string is words separated by spaces:

- `bold`, `italic`, `underline` and `dim`
- a text colour written `#rrggbb`, or one of the named colours `black`,
  `red`, `green`, `yellow`, `blue`, `magenta`, `cyan` and `white`, and their
  `bright-` forms, such as `bright-red`
- a background colour written `bg:#rrggbb`

A later word for the same thing wins. `highlight.DefaultTheme` is xcl's own
look, which uses only the named colours and leaves unlabelled text alone.
`With` returns a copy of a theme with some kinds styled differently, leaving
both themes as they were, and `xcl.WithTheme` prints with it:

<CodeTabs>
  <div slot="go">

```go
theme := highlight.DefaultTheme.With(highlight.Theme{
	highlight.Attribute: "#ff8800",
	highlight.Comment:   "italic #6a9955",
	highlight.String:    "bright-green bg:#202020",
})

err = xcl.PrintEntity(os.Stdout, db,
	xcl.WithFormatter(highlight.Terminal),
	xcl.WithTheme(theme),
)
```

  </div>
  <div slot="python">

```python
import xcl
from xcl.highlight import DEFAULT_THEME, Kind

theme = DEFAULT_THEME | {
    Kind.ATTRIBUTE: "#ff8800",
    Kind.COMMENT: "italic #6a9955",
    Kind.STRING: "bright-green bg:#202020",
}

cfg.print_entity(db, formatter=xcl.highlight.TERMINAL, theme=theme)
```

A theme is a mapping of `xcl.highlight.Kind` to style string. `DEFAULT_THEME` cannot be changed in place, and `|` gives a new theme with the default's styles and the given ones in their place.

  </div>
</CodeTabs>

Kinds are grouped into categories, and a kind the theme does not style takes
its category's style, then the style of `highlight.Text`, unlabelled text. So
styling `highlight.Comment` styles every comment, line, hash and block alike,
until the theme styles `highlight.LineComment` itself. A style is taken
whole, never merged with its category's: a theme with
`highlight.LineComment: "#ff0000"` writes line comments red and not italic,
whatever `Comment` says. `kind.Parent()` gives a kind's category.

A word a style does not understand, such as a misspelt colour, is skipped
when printing, so a theme never stops output. `Validate` reports every such
word, as one error for each joined together, each matching
`xcl.ErrInvalidStyle` with an `xcl.InvalidStyleError` detail naming the kind,
the style and the word:

<CodeTabs>
  <div slot="go">

```go
theme := highlight.DefaultTheme.With(highlight.Theme{
	highlight.Attribute: "bold orang",
})

if err := theme.Validate(); err != nil {
	log.Print(err)
}
```

  </div>
  <div slot="python">

```python
import logging

import xcl
from xcl.highlight import DEFAULT_THEME, Kind, validate

theme = DEFAULT_THEME | {Kind.ATTRIBUTE: "bold orang"}

try:
    validate(theme)
except xcl.InvalidStyleError as err:
    logging.warning("%s", err)
```

`validate` raises one `xcl.InvalidStyleError` naming every unknown word, one line for each, and its `words` holds a `(kind, style, word)` for each.

  </div>
</CodeTabs>

```text
style "bold orang" for Attribute: unknown word "orang"
```

Printed with that theme, attributes are bold and keep the terminal's own
colour.

### With an editor theme

`highlight.LoadVSCodeTheme` reads a VS Code colour theme and returns the
`highlight.Theme` it gives xcl's kinds, so tokens look the way the editor
shows them with that theme. The theme holds only the kinds the VS Code theme
styles; extend the default with it to keep xcl's style for the rest:

<CodeTabs>
  <div slot="go">

```go
file, err := os.Open("dark-plus.json")
if err != nil {
	return err
}
defer file.Close()

loaded, err := highlight.LoadVSCodeTheme(file)
if errors.Is(err, xcl.ErrInvalidTheme) {
	var detail *xcl.InvalidThemeError
	errors.As(err, &detail)
	log.Fatalf("theme: %s", detail.Reason)
}

theme := highlight.DefaultTheme.With(loaded)

err = xcl.PrintEntity(os.Stdout, db,
	xcl.WithFormatter(highlight.Terminal),
	xcl.WithTheme(theme),
)
```

  </div>
  <div slot="python">

```python
import sys

import xcl
from xcl.highlight import DEFAULT_THEME, TERMINAL, load_vscode_theme

try:
    loaded = load_vscode_theme("dark-plus.json")
except xcl.InvalidThemeError as err:
    sys.exit(f"theme: {err.details['reason']}")

theme = DEFAULT_THEME | loaded

cfg.print_entity(db, formatter=TERMINAL, theme=theme)
```

`load_vscode_theme` takes the theme file's path, or its contents as bytes. The engine converts it with the same rules as Go, so the theme is the same in both languages.

  </div>
</CodeTabs>

The theme is the JSON file a VS Code theme extension ships, and comments and
trailing commas are allowed, as the editor allows them. Only its
`tokenColors` are used: their text colours and their bold, italic and
underline styles. Each kind is styled as the theme styles its TextMate scope,
`kind.Scope()`, the name the xcl VS Code extension gives the same text, such
as `variable.other.property.xcl` for `highlight.Attribute`, by the editor's
own matching rules. In a terminal the theme's colours print as 24-bit colour,
and the loaded theme works with every other format too, including the
stylesheet below.

A theme that cannot be read, or is not valid, returns an error matching
`xcl.ErrInvalidTheme` rather than quietly falling back to the default
colours, and its `xcl.InvalidThemeError` detail says what was wrong, such as
`tokenColors[0].settings.foreground "#zz0000" is not a colour`. A theme that
relies on `include` is rejected the same way, since it does not hold its own
`tokenColors`.

### On a website

`highlight.HTML` writes one `<pre class="xcl">` block for a page. Each piece
of text that is not `highlight.Text` is in a `<span>` with its category's
class first, when its kind belongs to a category, then its kind's own, such as
`<span class="xcl-comment xcl-line-comment">`. Unlabelled text, such as
whitespace and braces, is written without a span, and all of it is escaped.
The theme is ignored, so your own stylesheet decides the colours. The
`database.postgres.main` entity above prints as:

```html
<pre class="xcl"><span class="xcl-block xcl-block-type">database</span> <span class="xcl-label xcl-type-label">&quot;postgres&quot;</span> <span class="xcl-label xcl-name-label">&quot;main&quot;</span> {
  <span class="xcl-attribute">location</span> <span class="xcl-operator">=</span> <span class="xcl-string">&quot;localhost&quot;</span>
  <span class="xcl-attribute">port</span>     <span class="xcl-operator">=</span> <span class="xcl-number">5432</span>

  <span class="xcl-block xcl-nested-block">timeouts</span> {
    <span class="xcl-attribute">connection</span> <span class="xcl-operator">=</span> <span class="xcl-number">10</span>
    <span class="xcl-attribute">keep_alive</span> <span class="xcl-operator">=</span> <span class="xcl-number">60</span>
  }
}
</pre>
```

The class names are a public contract, the same in every language xcl is used
from. Each kind's class is `xcl-` and its name in kebab case, and a kind that
is a category of its own, such as `highlight.Attribute`, has one class:

| Category | Category class | Kinds in it |
| --- | --- | --- |
| `Block` | `xcl-block` | `BlockType` `xcl-block-type`, `NestedBlock` `xcl-nested-block` |
| `Label` | `xcl-label` | `TypeLabel` `xcl-type-label`, `NameLabel` `xcl-name-label` |
| `Attribute` | `xcl-attribute` | |
| `String` | `xcl-string` | `StringEscape` `xcl-string-escape`, `Heredoc` `xcl-heredoc`, `HeredocMarker` `xcl-heredoc-marker`, `HeredocOperator` `xcl-heredoc-operator` |
| `Number` | `xcl-number` | |
| `Constant` | `xcl-constant` | |
| `Function` | `xcl-function` | `BuiltinFunction` `xcl-builtin-function` |
| `Reference` | `xcl-reference` | `Member` `xcl-member` |
| `Operator` | `xcl-operator` | |
| `Punctuation` | `xcl-punctuation` | `InterpolationBegin` `xcl-interpolation-begin`, `InterpolationEnd` `xcl-interpolation-end`, `TemplateDirective` `xcl-template-directive`, `Accessor` `xcl-accessor` |
| `Comment` | `xcl-comment` | `LineComment` `xcl-line-comment`, `HashComment` `xcl-hash-comment`, `BlockComment` `xcl-block-comment` |
| `Diff` | `xcl-diff` | `Inserted` `xcl-inserted`, `Deleted` `xcl-deleted`, `Changed` `xcl-changed` |
| `Problem` | `xcl-problem` | `Error` `xcl-error`, `Warning` `xcl-warning` |
| `Report` | `xcl-report` | `Summary` `xcl-summary`, `Location` `xcl-location`, `Gutter` `xcl-gutter`, `Detail` `xcl-detail` |

The `Diff` kinds mark what a change summary changes, and the `Problem` and
`Report` kinds the parts of an error report, so one stylesheet styles all
three outputs. `kind.Class()` gives a kind's class.

`highlight.WriteCSS` writes a stylesheet for these classes from any theme, the
default, your own or one loaded from the editor, as a starting point for your
site's styles. Every rule is scoped under `.xcl`, and categories come before
the kinds in them, so a kind's own rule wins:

<CodeTabs>
  <div slot="go">

```go
file, err := os.Create("xcl.css")
if err != nil {
	return err
}
defer file.Close()

err = highlight.WriteCSS(file, highlight.DefaultTheme)
```

  </div>
  <div slot="python">

```python
from pathlib import Path

from xcl.highlight import DEFAULT_THEME, css

Path("xcl.css").write_text(css(DEFAULT_THEME))
```

`xcl.highlight.css(theme)` returns the stylesheet as a string, identical to the one Go writes for the same theme.

### Writing a format

A format of your own is a `highlight.Formatter`, whose one method,
`Format(w io.Writer, theme highlight.Theme, tokens []highlight.Token) error`,
is given every token of the text at once, in order, so it can reason across
them, such as by line. Each `highlight.Token` has a `Kind` and its `Text`.
Unlabelled text, such as whitespace, braces and commas, is a token of kind
`highlight.Text`, so the tokens hold every byte exactly once and a format that
needs escaping sees all of it. `highlight.FormatterFunc` turns a function into
a formatter, and `theme.Style(token.Kind)` resolves a token's style the way the
built-in formats do, through its category and `Text`:

<CodeTabs>
  <div slot="go">

```go
var bbcode highlight.Formatter = highlight.FormatterFunc(
	func(w io.Writer, theme highlight.Theme, tokens []highlight.Token) error {
		var out strings.Builder
		for _, token := range tokens {
			style := theme.Style(token.Kind)

			text := token.Text
			if style.Bold {
				text = "[b]" + text + "[/b]"
			}
			if style.Italic {
				text = "[i]" + text + "[/i]"
			}
			if style.Foreground != "" {
				text = "[color=" + style.Foreground.Hex() + "]" + text + "[/color]"
			}

			out.WriteString(text)
		}

		_, err := io.WriteString(w, out.String())
		return err
	},
)

err = xcl.PrintEntity(os.Stdout, db, xcl.WithFormatter(bbcode))
```

  </div>
  <div slot="python">

```python
from xcl.highlight import hex_colour, style_for


class BBCode:
    def format(self, out, theme, tokens):
        for token in tokens:
            style = style_for(theme, token.kind)

            text = token.text
            if style.bold:
                text = "[b]" + text + "[/b]"
            if style.italic:
                text = "[i]" + text + "[/i]"
            if style.foreground:
                text = "[color=" + hex_colour(style.foreground) + "]" + text + "[/color]"

            out.write(text)


bbcode = BBCode()

cfg.print_entity(db, formatter=bbcode)
```

A format is any object with a `format(out, theme, tokens)` method, the `xcl.highlight.Formatter` protocol, and it writes to the stream `out`. Each `xcl.highlight.Token` has a `kind` and its `text`. `xcl.highlight.style_for(theme, kind)` resolves a style through its category and `TEXT`, and `xcl.highlight.hex_colour` gives a named colour as its fixed hex colour. For a known kind, `token.kind.parent` and `token.kind.css_class` give its category and HTML class. A kind from a newer engine that the package does not know arrives as its number, and `style_for` and `xcl.highlight.parent_of(number)` still take it to its category.

  </div>
</CodeTabs>

For the same entity it prints:

```text

  [color=#2472c8]location[/color] = [color=#e5e510]"localhost"[/color]
  [color=#2472c8]port[/color]     = [color=#d670d6]5432[/color]

  [color=#bc3fbc][b]timeouts[/b][/color] {
    [color=#2472c8]connection[/color] = [color=#d670d6]10[/color]
    [color=#2472c8]keep_alive[/color] = [color=#d670d6]60[/color]

```

`style.Foreground.Hex()` gives a named colour as the same fixed hex colour the
HTML and SVG formats use. A format can also match a kind or its category
directly, such as `token.Kind.Parent() == highlight.Comment` for every kind
of comment, and `token.Kind.Class()` and `token.Kind.Scope()` give its HTML
class and TextMate scope.

To format the tokens yourself, `xcl.EntityTokens` returns an entity's
configuration text labelled, taking the same encoding choices as
`EncodeEntity`, and `highlight.Tokenize` labels any configuration text you
already hold, such as a file read from disk, not only text encoded from an
entity. Joined, the tokens' text is exactly the text they were made from:

```go
tokens, err := xcl.EntityTokens(db, xcl.IncludeComputed())
if err != nil {
	return err
}

err = bbcode.Format(os.Stdout, highlight.DefaultTheme, tokens)

src, err := os.ReadFile("main.xcl")
if err != nil {
	return err
}

err = highlight.Terminal.Format(os.Stdout, highlight.DefaultTheme, highlight.Tokenize(src))
```

## For reading, not reprocessing

Configuration text is for people to read. By default references come out as
the literal values they resolved to, unless you ask for `ShowReferences`.
Comments and layout from the original file are not kept, and text including
provider-filled values does not validate, since xcl refuses a configuration
that sets them.
